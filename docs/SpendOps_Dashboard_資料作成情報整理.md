企画書、技術解説、発表スライドなどを作成する前に、アプリ概要、技術の選定理由、現状の課題、未確定事項を一か所へ整理する。

## 1. 要点

SpendOps Dashboardは、PayPayとクレジットカードの利用明細CSVを利用者が任意のタイミングで読み込み、月別・直近1年間・全期間の支出を確認するWebアプリである。

正式な対応形式はPayPay、JCB、三井住友VISAであり、3形式とも現行実装で対応済みである。横浜銀行を含む銀行CSV、収入・資産推移・予算管理、AWS料金分析は今回の対象外とする。

CSV原本は保存せず、日付単位に正規化した支出データと月別集計を使って画面表示・比較分析を行う。AWSの認証、API、保存、比較、Web配信まで実装済みだが、2026-07-23のTerraform Destroy後は公開基盤が停止している。Terraformの詳細は補足資料へ残す。

## 2. アプリ概要

### 2.1 解決したい課題

- 支払い元ごとに明細が分かれ、月全体で何にいくら使ったか把握しにくい。
- CSVごとに文字コード、ヘッダー位置、列構成、項目名が異なり、そのままではまとめて分析できない。
- 金額の一覧だけでは、支出が多いか少ないか、前月からどう変わったか判断しにくい。
- 毎日入力する家計簿は継続の負担が大きい。
- 他人との比較は参考になる一方、生明細の共有はプライバシー上の問題がある。
- 自動分類で判定できない利用先が「その他」に集まると、分析結果が役立ちにくくなる。

### 2.2 提供価値

- 任意のタイミングでCSVを読み込み、その日までの暫定状況を確認できる。
- 異なるCSVを共通形式へ正規化し、月別中心でまとめて確認できる。
- 支出総額、カテゴリ内訳、前月比、月ごとの推移を一画面で確認できる。
- 自分の過去や、条件を満たす匿名化された集団平均との差を比較軸にできる。
- 利用先の分類を本人が修正し、次回以降の取込へ反映できる。
- CSV原本や他人の生明細を共有せずに分析できる。

### 2.3 想定利用者

- PayPayや複数のクレジットカードなど、複数の決済方法を使っている人。
- 表計算やデータ管理に詳しくない人。
- 毎日の家計簿入力は難しいが、月に一度など任意のタイミングで振り返りたい人。
- 支出額だけでなく、自分の変化や比較基準も確認したい人。

### 2.4 基本的な利用の流れ

1. 利用者が対象サービスからCSVを取得する。
2. Web画面でCSVを選択する。
3. ブラウザがCSV形式を判定し、日付、金額、利用先、カテゴリ、取得元などを共通形式へ正規化する。
4. 取引を日付単位で扱い、月別集計を作成する。
5. 月別レポートで総額、内訳、推移、前月比、比較結果、明細を確認する。
6. 必要に応じて利用先のカテゴリを修正する。
7. ログイン中は、画面復元に必要な正規化済みデータ、月別集計、取込履歴、本人用分類ルールを本人の領域へ保存する。

### 2.5 対応CSV

| 取得元 | 文字コード・形式 | 取込方法 | 状態 |
|---|---|---|---|
| PayPay | UTF-8、ヘッダー行あり | CSVアップロード | 対応済み |
| JCB | Shift_JIS、先頭メタ情報の後に明細ヘッダー | CSVアップロード | 対応済み |
| 三井住友VISA | Shift_JIS、メタ情報を含む固定列形式 | CSVアップロード | 対応済み |
| 銀行 | - | - | 対象外 |

UTF-8での読取に失敗した場合はShift_JISを試す。複数ファイルを一度に選択でき、別々に読み込んだPayPayとカードを現在のセッション内で統合する。収入行は支出集計から除外する。

### 2.6 優先する画面・情報

最優先は月別レポート画面とする。

- 月間支出総額
- 前月比
- 取引件数
- カテゴリ別内訳
- 月ごとの支出推移
- 自分の過去との比較
- 匿名化された集団平均との差
- 支払い明細
- 分析結果から分かることと次の確認行動
- 取得元ごとの最終取込日（未実装）
- 未取込の取得元に対する警告（未実装）

### 2.7 現行実装で確認できる主な機能

- PayPay、JCB、三井住友VISAのCSV解析。
- 複数ファイル・複数支払い元の統合。
- 月別、直近12か月、全期間の支出集計。
- 固定11カテゴリの内訳と月別推移。
- 支出増加を赤、減少を青で示す前月比較。
- 明細の表示、利用先・コンビニチェーン単位の絞り込み。
- 利用先ごとのカテゴリ修正、修正用CSVの書出し・読戻し。
- 利用先名そのものを分類ルールへ保存しない、SHA-256照合値による本人別分類学習。
- Cognito認証、JWTで保護されたAPI、本人単位のデータ分離。
- 正規化済み取引、月別集計、取込履歴、分類ルールのDynamoDB保存。
- 他者5人以上などの条件を満たす場合の匿名比較と、不足時の合成参考値。
- フロントエンド46件、Lambda 24件、合計70件の自動テスト実績。

### 2.8 データとプライバシーの基本方針

#### 保存しないもの

- CSV原本、ファイル名、未加工行。
- カード番号、口座番号、パスワード、確認コード。
- 氏名、メール本文全文、住所、電話番号。
- CloudWatch LogsへのCSV全文や取引内容の出力。

#### 保存対象となり得るもの

- 本人ID。
- 正規化した取引日、金額、利用先、カテゴリ、支払い元。
- 月別集計、取込ID、取込日時、検証件数。
- 分類ルール用の支払い元、固定カテゴリ、利用先照合用SHA-256値。

#### 比較時の方針

- 他人の生明細は表示しない。
- 本人を除外し、暫定月を除外した集計値を使用する。
- 現行実装では、同月・同支払い種別の他ユーザーが5人以上の場合だけ実ユーザー平均を表示する。
- 条件を満たさない場合に表示する合成参考値は、実統計ではないことを明記する。
- 提出時には、分析対象の本人を含まないPayPayの実データを5人分用意する予定である。このため、現行の「本人を除く他ユーザー5人以上」という実比較条件を満たす。
- JCB、VISAなど、その他の取得元で同数の実データを用意することは難しい。

### 2.9 システム構成の概要

現行コードが想定する構成は次のとおりである。

```text
利用者のCSV
  ↓ ブラウザ内で解析・正規化
HTML / CSS / JavaScript製Webアプリ
  ↓ Cognito JWT付きリクエスト
API Gateway
  ↓
Lambda（入力検証・保存・レポート・比較）
  ↓
DynamoDB（取引・月別集計・取込履歴・分類ルール）

静的Web資産: 非公開S3 → CloudFront
監視: CloudWatch Logs / Metrics
```

AWS基盤は2026-07-23に削除済みで、現在は公開サイト、ログイン、API、クラウド保存を利用できない。ソースコード、Terraform定義、テスト、設計資料はローカルに保持しており、AWSの論理構成とアプリ側の実装は残っている。現在利用できるのは、空設定の`app-site/config.js`を使った未ログインのローカル分析である。AWSを再構築する場合は、新しいPlan、料金、公開範囲を確認してから実施する。

## 3. 技術の選定理由

### 3.1 技術選定一覧

| 技術・方式 | 用途 | 選定理由 | 注意点 |
|---|---|---|---|
| HTML / CSS / JavaScript | Web画面、CSV解析、集計、グラフ描画 | 小規模な学校課題として構成を説明しやすく、ビルド環境なしでも動かせる。ブラウザ内でCSV処理を完結させやすい | 機能増加により`script.js`が大きくなり、保守性が下がりやすい |
| ブラウザ内CSV解析 | 形式判定、文字コード変換、正規化 | CSV原本をサーバーへ送らずに済み、金融情報の不要な保存・送信を避けられる | 端末性能、ブラウザ互換性、大容量ファイルに影響される |
| UTF-8 / Shift_JIS対応 | 各社CSVの読取 | PayPayとカードで異なる文字コード・形式を吸収するため | 対応済み3形式以外の取込は保証しない |
| AWS Lambda（Python） | 入力検証、保存、レポート、比較API | 常時サーバーを管理せず、利用時だけ処理できる。検証・集計処理を分離しやすい | 1つのLambdaへ責務が集中すると保守しにくい。現在AWS基盤は停止中 |
| API Gateway HTTP API | Web画面とLambdaの接続 | HTTPS API、ルーティング、Cognito JWT認可をマネージドで実現できる | CORS、公開範囲、認可設定を誤ると情報漏えいにつながる |
| Amazon Cognito | 登録、メール確認、ログイン、一般ユーザー・管理者の分離 | 認証基盤を独自実装せず、JWTとユーザーグループを利用できる | メールアドレスを扱うため、資料・ログへ出さない運用が必要 |
| Amazon DynamoDB | 取引、月別集計、取込履歴、分類ルール | ユーザーID・月・取引キーを中心としたアクセスに合わせやすく、サーバーレス構成と相性がよい。PAY_PER_REQUESTで小規模利用に合わせやすい | 横断集計や複雑な検索には工夫が必要。現行は1回の保存・明細取得が最大5,000件 |
| Amazon S3 | 静的Web資産 | HTML、CSS、JavaScriptを低運用負荷で配置できる | CSV原本の保存先には使用しない。バケットは非公開を前提とする |
| Amazon CloudFront + OAC | Web配信、HTTPS、非公開S3への限定アクセス | S3を直接公開せず、安全に静的サイトを配信できる | 独自ドメイン、証明書、キャッシュ更新の運用が必要 |
| Amazon CloudWatch | API・Lambdaの監視 | エラーや稼働状況を確認できる | CSV全文、個人情報、金融情報をログへ出さない設計が必須 |
| SHA-256照合値 | 本人別分類ルールの利用先照合 | 分類ルール用DBへ利用先名そのものを保存せず、同一利用先を照合できる | ハッシュ化は匿名化と同義ではない。入力候補が推測可能な場合への説明が必要 |
| Terraform | AWS構成のコード化・再現 | 構成、権限、保護設定をレビュー可能な形で再現できる | 技術の詳細は本編ではなく補足資料へ掲載する |
| Node.jsテスト / Python unittest | 回帰確認 | CSV解析、集計、認証、比較、保存処理を自動確認できる | 現在の実績はフロントエンド46件、Lambda 24件、合計70件 |

### 3.2 技術選定の中心となる考え方

#### CSV原本を外へ出さない

金融データを扱うため、CSV原本をサーバーへ送る方式ではなく、ブラウザ内で解析して必要な項目だけを正規化する方式を選んでいる。技術上の便利さより、保存・送信する情報を減らすことを優先した設計である。

#### 月別分析と日付単位保存を分ける

画面では月別の分かりやすさを優先する一方、明細復元、絞り込み、再集計ができるよう取引は日付単位で扱う。表示用の月別集計だけではなく、正規化済み取引も本人単位で保持する構成である。

#### マネージドサービスで運用範囲を絞る

認証、API、データ保存、配信、監視にAWSのマネージドサービスを使い、独自サーバーや独自認証の管理を減らす。個人開発で扱える運用範囲に絞りつつ、権限分離や暗号化、削除保護を説明できる構成としている。

#### 比較とプライバシーを両立する

他人の明細を並べるのではなく、人数条件を満たす月別集計だけを比較に使う。比較できない場合は実平均を返さず、合成値を表示する場合も参考値であることを明示する。

### 4.2 機能面の課題

- 取得元ごとの最終取込日と未取込警告は、取込日時データがあるものの画面表示が未実装である。
- 不正行は件数表示のみで、失敗行番号と行別理由の表示が未実装である。
- PayPay、JCB、VISAの返金・取消表現は、実例に基づく検証が不足している。
- PayPayチャージとカード明細など、取得元をまたぐ二重計上を自動解消しない。
- 1回の保存と明細再取得は最大5,000件である。
- 退会APIは誤操作防止のためHTTP 501で無効化されている。
- 管理者機能は取込バッチ総数の確認が中心で、管理画面や詳細エラー確認は未実装である。

### 4.3 分析・データ面の課題

- 長期保持している匿名比較データは3人分であり、現行の「他5人以上」という実比較条件を満たさない。
- 合成参考値は実統計ではなく、比較結果の信頼性を誤解させない説明が必要である。
- 自動分類と利用先の表記揺れは継続改善が必要である。
- 月途中の暫定分析と完全月を明確に区別し続ける必要がある。

### 4.4 セキュリティ・プライバシー面の課題

- 正規化済み利用先は本人の明細復元に必要だが、金融行動を推測できる情報でもある。保存目的、保持期間、削除方法の説明が必要である。
- SHA-256照合値は利用先名を直接保存しない工夫だが、匿名化を保証するものではない。資料では「利用先名そのものを保存しない」と説明し、「完全匿名」と断定しない。
- 現在、退会時の本人データ削除が有効化されていない。
- AWS再構築時はCognito、DynamoDB、S3、API Gateway、IAM、ログ設定を改めて確認する必要がある。

### 4.5 運用・公開面の課題

- 2026-07-23にAWS基盤を削除したため、公開E2E、ログイン、クラウド保存、実ユーザー比較を現在は確認できない。
- 公開用Cloudflare DNSが削除済みCloudFrontを参照している可能性がある。
- AWS再構築、外部公開、デプロイは費用・公開範囲・個人情報へ影響するため、別途承認が必要である。
- Terraformの構成・安全設定・再構築手順は補足資料へまとめ、本編ではアプリの利用価値とAWS構成を中心に説明する。

### 4.6 資料面の課題

- README、ガードレール、引継ぎ、Notion、企画書、draw.io、ビジュアルブリーフの仕様が完全には一致していない。
- 既存のPowerPoint、Word資料、draw.ioはPayPay・JCB・VISA、銀行対象外の前提であり、今回の対象方針とは一致している。
- AWSの停止状態、Terraform stateが0エントリであること、Terraformを補足資料へ置く方針は既存資料へ反映する必要がある。
- AWS削除前の公開状態を記した資料があり、現在も公開中であるように見える記述を修正する必要がある。
- 目標仕様、現行実装、将来構想を同じ時制で説明すると誤解を招くため、資料ごとに時点を明記する必要がある。

## 5. 不明点・決定が必要な事項

### 5.1 今回解決した事項

- 正式対応形式はPayPay、JCB、三井住友VISAとする。
- 銀行CSVを正確に取り込む機能は今回の設計・実装対象外とする。
- AWSの認証、API、保存、比較、Web配信は実装済みだが、現在のAWS基盤は削除済みである。
- Terraformの詳細は補足資料へ残す。
- PayPayは提出時に、分析対象の本人を含まない5人分の実データを用意する予定であり、現行の実比較条件を満たす。
- JCB、VISAなど、PayPay以外で同数の実データを用意することは難しい。

### 5.2 引き続き決定が必要な重要事項

1. **PayPay以外の比較表示**  
   実データが不足するJCB・VISAでは、合成参考値を表示するか、自分の過去との比較だけにするか、比較待ちと表示するかを決める。

2. **AWSを再構築するか**  
   READMEでは再構築を必須としておらず、「再構築を行う場合」に公開E2Eを確認する扱いである。再構築する場合は実施時期を決める。

### 5.3 実装前に実例確認が必要な事項

- PayPayの返金・取消・チャージのCSV表現。
- JCBの速報・確定・取消・返金のCSV表現。
- 三井住友VISAの固定列の正式な意味と取消・返金表現。
- 同じCSVの再取込、期間が重なるCSV、取得元をまたぐ同一支出の重複判定基準。

### 5.4 UI・運用上の未決事項

- 何日間取り込まれていなければ「未取込警告」を表示するか。
- 取得元ごとの最終取込日は、CSV内の最終取引日とアップロード日時のどちらを表示するか。
- 正規化済み取引の保持期間と、利用者が自分で削除する手順。
- 5,000件を超える明細の分割取込・ページングを提出版で扱うか。
- エラー行に利用先や金額などの金融情報が含まれる場合、どこまで画面へ表示するか。

### 5.5 制作する資料について確認が必要な事項

- 資料の提出先と主な読者。
- 企画書、要件定義書、技術解説、発表スライドのうち必要な成果物。
- ファイル形式、ページ数、発表時間、提出期限、採点基準。
- 現行のGoogle Slides / Google Docsを更新するか、新規資料を作るか。
- 実画面のスクリーンショットを使う場合、どの画面を掲載するか。掲載画像には実在の金融情報を使わない。

- PayPay、JCB、三井住友VISAはCSVアップロードで取り込む。
- 取引は日付単位で扱い、分析・表示は月別を中心にする。
- PayPay、JCB、三井住友VISAは支出分析の対象である。
- 銀行CSVは今回の設計・実装対象外である。
- 月別レポート画面を最優先にする。
- 取得元ごとの最終取込日と未取込警告は未実装である。
- CSV原本、未加工行、カード番号、口座番号、認証情報を保存しない。
- 他人の生明細を表示せず、比較には匿名化・集計した値を使う。
- AWS機能のコードとTerraform定義は実装済みだが、AWS基盤は削除済みで現在停止している。
- Terraformの詳細は補足資料へ掲載する。
- PayPayは提出時に、分析対象の本人を含まない5人分の実データを用意する予定であり、現行の実比較条件を満たす。

## 7. 現時点では断定を避ける事項

- あらゆるCSVを形式確認なしで正確に取り込めること。
- 銀行CSVに対応していること。
- 取得元ごとの最終取込日・未取込警告が実装済みであること。
- 現在も公開サイト、ログイン、API、クラウド保存が利用できること。
- PayPay以外でも5人以上の実ユーザーデータによる比較を表示できること。
- 返金、取消、異なる取得元間の二重計上を完全に処理できること。
- SHA-256照合値だけで完全な匿名化が実現できること。
- 退会時の本人データ削除が現在利用できること。
